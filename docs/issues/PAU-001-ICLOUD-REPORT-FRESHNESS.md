# PAU-001：iCloud 更新晚于日报快照，导致日报漏项

- 状态：Open，已核实，尚未修复。
- 优先级：P1，报告完整性问题；同一流程也可能影响周报。
- 记录日期：2026-10-14（北京时间）。
- 范围：Windows 本地 iCloud CSV、登录补发、快照冻结与已发回执。与前一天的 SMTP 不确定发送问题不同。

## 已核实的时间线

| 北京时间 | 观察 |
| --- | --- |
| 2026-10-14 08:48:06 | 日报生成并冻结当时的本地 CSV 快照 |
| 2026-10-14 08:48:09 | 对应日报经 QQ 发出，Gmail 实收 |
| 2026-10-14 08:48:30 | Windows 镜像更新，包含一条此前未纳入邮件的晚间新增记录 |

读取实际邮件的原始 MIME 后，确认正文和完整 CSV 附件均未包含该新增记录；附件散列与更新前的 `.previous` 镜像一致。随后本地已验证镜像包含该记录。证据表明邮件使用了当时可读但尚不完整的本地来源，而非只在 HTML 筛选阶段漏行。

镜像写入时间证明本地镜像何时更新，不能精确证明手机上传或 iCloud 服务端传播何时完成。账户、原始 CSV、具体活动/分钟数、消息 ID 与完整散列留在私有证据中，不发布。

## 原因与现有行为

`PaulatimDispatch.Snapshot()` 同步并检查来源、镜像、状态与原始附件的散列一致性。这可以证明本地快照一致，**不能证明 iCloud 已收到并下载全部手机更新**。登录后的第一份可读文件可能仍是旧版本。

发送后该周期进入已发回执；稍后到达的新增记录不会改写已发送邮件，也不会自动触发更正版本。因此可能出现“本地有完整记录，已收日报仍缺项”。已有防重发机制应保留，不能通过删除回执来解决。

## 待设计与实现

1. 登录补发前增加有上限的同步等待与多次来源复核；记录观察窗口和来源变化。连续不变只是本地稳定的证据，不能宣称云端完整。
2. 冻结后至提交发送意图之前再复核来源；发现变化时重新生成未发送候选。已有尝试/不确定发送的冻结载荷不能静默替换。
3. 在报告中明确快照时间与同步边界；读取失败、发生变化或无法确认就绪时写可见状态，避免仅有后台日志。
4. 对已发周期后来新增/变更记录，检测并提示“日报可能需要更正”。更正版应有独立版本/回执并关联原报告，不能覆盖旧回执或自动重复发原报告。更正发送策略须另行确认。

## 验收方案

- 合成来源先提供旧 CSV，模拟约24秒后出现晚间新行；确认等待/复核能在发送前纳入新行，并且只发送一次。
- 覆盖来源持续变化、更新超过等待上限、文件不可读/无网络；状态准确且不截断、不丢历史。
- 覆盖来源在冻结后、发送意图前及 SMTP 不确定之后变化；只允许未发送候选更新，不改变已尝试的冻结载荷。
- 覆盖已发回执存在时晚到数据：原报告/回执保留，更正提示与版本幂等，不盲目重发。
- 日报/周报边界、原 CSV 字节附件和现有发送故障保护回归保持通过。
- 用虚构手机记录验证真实 iCloud 链路；模拟稳定窗口不能替代实机验证或提供永久完整性保证。

本次仅登记问题和候选方向，没有修改程序、任务、源数据或回执，也没有发送更正邮件。
