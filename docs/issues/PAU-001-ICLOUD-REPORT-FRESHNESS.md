# PAU-001：iCloud 更新晚于日报快照，导致日报漏项

- 状态：用户指定的午夜来源时间门禁已实现、验收并部署到正式任务；无需人工确认。
- 优先级：P1，报告完整性问题；同一流程也可能影响周报。
- 记录日期：2026-10-14（北京时间）。
- 范围：Windows 本地 iCloud CSV、登录补发、快照冻结与已发回执。与前一天的 SMTP 不确定发送问题不同。

## 已核实的时间线

| 北京时间 | 观察 |
| --- | --- |
| 2026-10-14 08:48:06 | 日报生成并冻结当时的本地 CSV 快照 |
| 2026-10-14 08:48:09 | 对应日报经 QQ 发出，Gmail 实收 |
| 2026-10-14 08:48:30 | Windows 镜像更新，包含一条此前未纳入邮件的晚间新增记录 |

读取实际邮件的原始 MIME 后，确认正文和完整 CSV 附件均未包含该新增记录；附件散列与更新前的 `.previous` 镜像一致。随后本地已验证镜像包含该记录。证据表明邮件使用了当时可读但尚不完整的本地来源，而非只在 HTML 筛选阶段漏行。

镜像写入时间证明本地镜像何时更新，不能精确证明手机上传或 iCloud 服务端传播何时完成。账户、原始 CSV、具体活动/分钟数、消息 ID 与完整散列留在私有证据中，不发布。

## 原因与现有行为

`PaulatimDispatch.Snapshot()` 同步并检查来源、镜像、状态与原始附件的散列一致性。这可以证明本地快照一致，**不能证明 iCloud 已收到并下载全部手机更新**。登录后的第一份可读文件可能仍是旧版本。

发送后该周期进入已发回执；稍后到达的新增记录不会改写已发送邮件，也不会自动触发更正版本。因此可能出现“本地有完整记录，已收日报仍缺项”。已有防重发机制应保留，不能通过删除回执来解决。

## 原候选方向

1. 登录补发前增加有上限的同步等待与多次来源复核；记录观察窗口和来源变化。连续不变只是本地稳定的证据，不能宣称云端完整。
2. 冻结后至提交发送意图之前再复核来源；发现变化时重新生成未发送候选。已有尝试/不确定发送的冻结载荷不能静默替换。
3. 在报告中明确快照时间与同步边界；读取失败、发生变化或无法确认就绪时写可见状态，避免仅有后台日志。
4. 对已发周期后来新增/变更记录，检测并提示“日报可能需要更正”。更正版应有独立版本/回执并关联原报告，不能覆盖旧回执或自动重复发原报告。更正发送策略须另行确认。

## 验收方案

- 合成来源先提供旧 CSV，模拟约24秒后出现晚间新行；确认等待/复核能在发送前纳入新行，并且只发送一次。
- 覆盖来源持续变化、更新超过等待上限、文件不可读/无网络；状态准确且不截断、不丢历史。
- 覆盖来源在冻结后、发送意图前及 SMTP 不确定之后变化；只允许未发送候选更新，不改变已尝试的冻结载荷。
- 覆盖已发回执存在时晚到数据：原报告/回执保留，更正提示与版本幂等，不盲目重发。
- 日报/周报边界、原 CSV 字节附件和现有发送故障保护回归保持通过。
- 用虚构手机记录验证真实 iCloud 链路；模拟稳定窗口不能替代实机验证或提供永久完整性保证。

## 当前规则：iCloud来源更新时间严格晚于00:00:00

用户明确指定：每天发送前检查iCloud数据时间；严格晚于发送当天北京时间 `00:00:00` 才发，否则先抓取快照、再次检查。用户随后确认所指为iCloud数据，而非实际截图。

程序使用 `source_modified_at_utc`（来自配置指向的 Windows iCloud CSV 的修改时间），不是 `report-data.json` 的写入时间，也不是重新运行时必然推进的 `snapshot_at_utc`。午夜前的来源即使今早重新抓取，仍不合格。`00:00:00` 整点不通过，之后的时间才通过；未来时间、缺少时区和损坏字段拒绝。

1. 到期报告每次先运行同步程序，重新读取iCloud来源并生成快照；读取失败或原始来源/镜像/状态/附件散列不一致时不发。
2. 检查来源修改时间及快照时间。两者须晚于当天北京时间午夜、不晚于当前时间，且快照不能早于来源更新。若不合格，状态为 `waiting_source`，不增加发送次数、不创建发送任务、不改回执；下个定时检查再次抓取并检查。
3. 最后复核散列和来源修改时间，持有只读共享锁直到发送结束，禁止来源在此窗口被写入或替换。提交意图前重新检查午夜条件，跨日时也要按新的发送日检查。
4. 日报、周报及验证邮件使用同一时间规则。既有防重发及不确定发送保护保留；旧冻结附件若与当前来源不同则拒绝，不替换已尝试载荷。
5. 取消前一版的120秒观察与人工来源确认要求；`source-ready.json` 不再参与门禁，确认脚本已从源码及正式安装移除。来源日期不合格时不通过人为修改时间戳绕过。

这是用户接受的时间阈值：Windows iCloud可以保留手机端原始修改时间，重新下载/读取不一定让这个时间变成今天。若当天午夜后没有来源更新，日报会继续等待。该阈值不能证明所有尚不可见的云端更新均已到达。

## 验收结果

- 17项时钟/门禁/发送故障测试：午夜前、午夜整点、午夜后一瞬间、UTC换算、其他时区、未来时间、快照早于来源、跨日、闰日、旧来源新快照、约24秒晚到、源文件锁以及冻结载荷保护，全部通过。
- 11项真实同步/控制器进程测试：QQ和Gmail旧来源都被阻止且次数/回执不变；来源缺失保留镜像；刷新后新行进入正文来源及原字节附件、无需人工确认便通过门禁。QQ正路径抵达发送配置预检，使用不存在的合成SMTP配置阻止任何实际外发；Gmail正路径只调用快照与门禁，不启动真实邮件执行器。
- 22项同步、28项邮件自测、4项邮件进程检查、18项SMTP故障、5项命名/附件回归测试通过，合计105项。脱敏结果见 [freshness-results.json](../freshness-results.json)。没有真实测试发信或手机端测试。

- 正式入口返回0、状态 `idle`；当前周期已有回执，没有新增发送。
- 任务XML、来源/邮件/SMTP配置及两份回执账本均与备份一致。原人工确认脚本已备份并移除，无需手动确认后才发。
- 只读核验当前真实来源与快照，时间门禁判定为不合格；真实来源不因抓取动作被人为推进时间。下一次报告到期时，程序会继续自动刷新检查，符合午夜标准后才能发送。
