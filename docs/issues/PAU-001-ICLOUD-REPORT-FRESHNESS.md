# PAU-001：iCloud 更新晚于日报快照，导致日报漏项

- 状态：严格发送门禁已实现、通过离线验收，并于2026-10-14部署到正式任务；手机/iCloud完整性实测及自动完成标记仍待办。
- 优先级：P1，报告完整性问题；同一流程也可能影响周报。
- 记录日期：2026-10-14（北京时间）。
- 范围：Windows 本地 iCloud CSV、登录补发、快照冻结与已发回执。与前一天的 SMTP 不确定发送问题不同。

## 已核实的时间线

| 北京时间 | 观察 |
| --- | --- |
| 2026-10-14 08:48:06 | 日报生成并冻结当时的本地 CSV 快照 |
| 2026-10-14 08:48:09 | 对应日报经 QQ 发出，Gmail 实收 |
| 2026-10-14 08:48:30 | Windows 镜像更新，包含一条此前未纳入邮件的晚间新增记录 |

读取实际邮件的原始 MIME 后，确认正文和完整 CSV 附件均未包含该新增记录；附件散列与更新前的 `.previous` 镜像一致。随后本地已验证镜像包含该记录。证据表明邮件使用了当时可读但尚不完整的本地来源，而非只在 HTML 筛选阶段漏行。

镜像写入时间证明本地镜像何时更新，不能精确证明手机上传或 iCloud 服务端传播何时完成。账户、原始 CSV、具体活动/分钟数、消息 ID 与完整散列留在私有证据中，不发布。

## 原因与现有行为

`PaulatimDispatch.Snapshot()` 同步并检查来源、镜像、状态与原始附件的散列一致性。这可以证明本地快照一致，**不能证明 iCloud 已收到并下载全部手机更新**。登录后的第一份可读文件可能仍是旧版本。

发送后该周期进入已发回执；稍后到达的新增记录不会改写已发送邮件，也不会自动触发更正版本。因此可能出现“本地有完整记录，已收日报仍缺项”。已有防重发机制应保留，不能通过删除回执来解决。

## 原候选方向

1. 登录补发前增加有上限的同步等待与多次来源复核；记录观察窗口和来源变化。连续不变只是本地稳定的证据，不能宣称云端完整。
2. 冻结后至提交发送意图之前再复核来源；发现变化时重新生成未发送候选。已有尝试/不确定发送的冻结载荷不能静默替换。
3. 在报告中明确快照时间与同步边界；读取失败、发生变化或无法确认就绪时写可见状态，避免仅有后台日志。
4. 对已发周期后来新增/变更记录，检测并提示“日报可能需要更正”。更正版应有独立版本/回执并关联原报告，不能覆盖旧回执或自动重复发原报告。更正发送策略须另行确认。

## 验收方案

- 合成来源先提供旧 CSV，模拟约24秒后出现晚间新行；确认等待/复核能在发送前纳入新行，并且只发送一次。
- 覆盖来源持续变化、更新超过等待上限、文件不可读/无网络；状态准确且不截断、不丢历史。
- 覆盖来源在冻结后、发送意图前及 SMTP 不确定之后变化；只允许未发送候选更新，不改变已尝试的冻结载荷。
- 覆盖已发回执存在时晚到数据：原报告/回执保留，更正提示与版本幂等，不盲目重发。
- 日报/周报边界、原 CSV 字节附件和现有发送故障保护回归保持通过。
- 用虚构手机记录验证真实 iCloud 链路；模拟稳定窗口不能替代实机验证或提供永久完整性保证。

## 2026-10-14 实现：来源未确认则不发送

采用严格模式，所有配置默认生效，没有自动退回“文件能读就发”的开关：

1. 每次到期检查仍执行来源同步及四方散列核对。跨分钟检查观察同一散列至少120秒；相邻观察超过90秒、散列变化或时钟倒退会重新等待。不阻塞进程睡眠，登录后的旧快照不会立即发送。
2. 稳定观察不是云端就绪证明。另需所有者明确确认手机导出与 Windows CSV 完整，并生成 `source-ready.json`：绑定原始 CSV SHA-256、已完成的北京时间日期及确认时间。确认必须发生在覆盖日期结束之后，未来时间、坏格式、缺失标记、旧散列和不足周期均拒绝。
3. 缺少就绪条件时显示 `waiting_source`，不增加发送次数、不创建外部发送任务、不改已发回执。每日确认只覆盖指定闭合日期；进入新周期需再次确认，即使当天无新增记录。
4. 最后复核后持有来源只读共享锁直到发送结束，禁止本地来源在此窗口被写入或替换。每个发送意图前再次核对确认。QQ 重试额外核验实际冻结附件：若它与当前来源不同，保留原载荷和账本并拒绝发送；不静默替换已尝试邮件。
5. 验证邮件也受门禁约束，要求已闭合日期（验证当天的前一天）被确认；它仍是当天部分记录的预览，不代表当天完整。

### 确认操作

先人工核对手机导出和 Windows CSV 的全部记录完整，然后获取**已核对导出**的散列。不得把本机散列计算成功本身当作手机导出完整的证据。

```powershell
# 仅在核对完整来源后运行；日期和散列替换为实际核对结果。
.\Paulatim\Confirm-SourceReady.ps1 -ThroughDate '2026-10-13' `
  -ExpectedSha256 'REPLACE_WITH_REVIEWED_64_CHARACTER_SHA256' `
  -ConfirmCompleteExport -InstallationDirectory 'C:\PATH\TO\ACTIVE_INSTALLATION'
```

该脚本不发邮件、不修改来源或回执；它与控制器使用同一邮件锁，来源发生变化时拒绝写确认。标记位于实际安装目录并被 Git 忽略。后续手机新增导致来源散列变化时，原确认立即不匹配；需重新核对和确认。部署新控制器而没有确认时，正式报告将保持等待。

### 验收结果

- 新增17项离线故障/时钟/发送测试，10项真实进程及确认脚本测试，全部通过。覆盖约24秒晚到、持续变化、稳定旧文件无确认、断续观察、日期/散列/确认损坏、周报覆盖、源文件锁、旧冻结载荷以及不确定发送。
- 两个真实控制器进程路径（QQ、Gmail）都验证：无确认或晚到更新使确认失效时，不创建发送工作、不增加次数，旧回执字节不变。新 CSV 在同步快照中含新增行，但尚未重新确认时仍不发。
- 原22项同步测试、28项邮件自测、4项邮件进程检查、18项SMTP故障测试、5项命名及附件测试通过；合计104项。脱敏结果见 [freshness-results.json](../freshness-results.json)。没有网络发信或手机实测。

### 保证与剩余边界

本版本保证**没有匹配的完整来源确认就不提交发送**，并阻止已知旧冻结附件发送；不保证所有者错误确认或尚不可见的云端更新能被自动识别。现有四列 CSV 不含手机端完成标记，自动证明云端完整需要另外设计手机端带内容散列/版本的完成协议。单纯延长等待不会消除这个边界。

已发报告保持原样，不删除回执、不自动补发。已发后晚到数据的自动更正提示/版本化更正仍待实现。手机端自动完成协议仍需另外设计；不能把本次严格门禁验收称为云端自动完整性验收。

用户随后明确要求修复正在运行的正式日报，授权正式部署。使用 `Deploy-Freshness.ps1`（Windows PowerShell 5.1）先预检，核对任务所属路径、到期列表为空和缺少来源确认确实被拒绝；持有邮件/SMTP锁、保留私有备份后替换正式控制器，并安装确认脚本。没有生成任何来源完整性确认。

- 安装控制器 SHA-256 与已验收构建一致：`e7a6aa026a4a0e7af8be2adfa1430e74888cd961ff776dca81d9add76b5a9db3`。
- 正式入口运行返回0、状态 `idle`；当前周期已经有回执，因此没有新增发送。
- 原任务XML、来源/邮件/SMTP配置及两份回执账本均与备份一致。没有重建任务、清除回执或更换来源。
- 正式目录尚无 `source-ready.json`，下一次有报告到期时会等待稳定观察及完整来源确认。新保护已经接入正式任务，不再只是仓库源码。
- 二进制回滚只恢复程序，不恢复旧回执覆盖新账本。私有备份和生产文件均未上传。
